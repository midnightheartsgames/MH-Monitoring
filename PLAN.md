# MH Monitoring на Rust — план реализации

Документ самодостаточный. Он написан для сессии, у которой нет истории предыдущего проекта.
Всё, что здесь помечено как «проверено», установлено экспериментально на реальной машине, а не
взято из документации. Эти факты стоили дня отладки — не переоткрывайте их.

---

## 1. Что строим

Компактный overlay-монитор производительности для Windows 10/11: GPU / CPU / RAM / FPS,
frametime-график, always-on-top поверх игр, click-through, трей, глобальные хоткеи.

Заменяет существующее приложение на Kotlin + Compose Desktop (`I:\IdeaProjects\MH Monitor`).
Тот проект работает, но упирается в две вещи: каждый кусок нативной поверхности Windows требует
ручных JNA-привязок (структуры, раскладки, callbacks — ошибка даёт segfault, а не исключение), и
дистрибутив тянет JRE (MSI ~73 МБ). Впереди ETW-потребитель, NVML, ADLX, служба Windows — то есть
нативной поверхности будет только больше.

**Старый проект не удалять.** Он — референс по неочевидному поведению Win32 (layered-окно,
перехват topmost, job objects) и источник алгоритмов для переноса (§7).

## 2. Проверенные факты — прочитать до написания кода

### 2.1. Осиротевшая ETW-сессия ломает захват кадров на всей машине

Самый дорогой урок. Realtime ETW-сессия **переживает процесс, который её создал**. Если её никто
не вычитывает, буферы переполняются и поток событий деградирует для всех потребителей.

Наблюдалось так: Intel PresentMon запускался успешно, сообщал `warning: ~200000 ETW events were
lost` и выдавал **ровно ноль** строк CSV. Одновременно переставал работать оверлей NVIDIA
(FrameView), показывая N/A. Причина — ровно одна брошенная сессия. Хронология:

| Замер | Живая сирота | Результат |
|---|---|---|
| A–D | `PresentMon` (имя по умолчанию, от убитого приложения) | 0 кадров, ~200k потеряно |
| E | `MHMonitor-31216-1` (от убитого приложения) | 0 кадров, 197k потеряно |
| **F** | **нет** | **340 КБ CSV, 718 строк, потерь нет** |

PresentMon нужны **парные** события (Present из DXGI + завершение из DxgKrnl). При такой потере у
почти каждого кадра теряется половина пары, поэтому на выходе ноль, а не «меньше кадров».

**Требования, невыполнение которых воспроизведёт этот баг:**

1. Имя сессии — **одно на запуск приложения**, а не на каждый захват. Схема `MHMonitor-<pid>`.
   Уникальное имя на каждую смену цели оставляет по сироте на переключение.
2. Никогда не использовать имя по умолчанию `PresentMon` — оно общее для всех инструментов на нём.
3. Останавливать свою сессию явно **на каждом пути выхода**: конец захвата, смена цели, закрытие
   приложения, паника.
4. При старте подметать сессии по префиксу `MHMonitor-`, кроме своей, — после падения или
   принудительного убийства сирота живёт до перезагрузки.
5. Диагностика: `logman query -ets` от админа; остановка `logman stop "<имя>" -ets`. В Rust —
   `ControlTraceW(0, name, &props, EVENT_TRACE_CONTROL_STOP)` из `windows` crate.

### 2.2. Дочерний процесс нельзя завершать мягко средствами JVM/Rust по умолчанию

На Windows `TerminateProcess` (это же `Process::kill()` в Rust и `Process.destroy()` в Java) не
даёт ребёнку выполнить очистку. PresentMon не успевает вызвать `ControlTrace(STOP)` → сирота.
Отсюда п. 2.1.3: сессию гасим **мы**, по известному нам имени, а не надеемся на ребёнка.
Вариант с `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT)` в отдельной группе процессов работает, но
менее надёжен, чем прямая остановка сессии.

### 2.3. Realtime ETW требует прав — и это решается установкой, а не выбором источника

`StartTrace` с `EVENT_TRACE_REAL_TIME_MODE` требует администратора **или** членства в группе
`Performance Log Users`. Это верно и для PresentMon, и для собственного потребителя. Свой ETW-ридер
**не убирает** UAC.

Решения, оба разовые, на этапе установки:
- служба под системой держит сессию, UI работает без элевации и общается с ней через named pipe
  (так устроены Intel PresentMon 2.x и NVIDIA App);
- инсталлятор добавляет пользователя в `Performance Log Users`.

Решение принять **до** написания процессной модели — ретрофит дорогой.

### 2.4. Прямое чтение DXGI/D3D9 слепо к Vulkan и OpenGL

Собственный ETW-потребитель `Microsoft-Windows-DXGI` + `Microsoft-Windows-D3D9` видит D3D9/10/11/12.
Vulkan и OpenGL через эти провайдеры не проходят — PresentMon покрывает их через `DxgKrnl`.
Подтверждено независимо: сторонний монитор с таким же подходом документирует отсутствие поддержки
Vulkan.

**Уточнено измерением (см. §2.11 и `spikes/etw-frames/COVERAGE.md`):** про Vulkan это
утверждение **не подтвердилось** — Dota 2 в режиме Vulkan даёт события `Microsoft-Windows-DXGI`
и считается корректно. Про OpenGL подтвердилось: Ion Fury не виден совсем. Замеры сделаны только
на NVIDIA и только в оконном/безрамочном режиме, поэтому покрытие Vulkan — наблюдение о
конкретной реализации WSI, а не гарантия.

**Вывод: свой ETW-ридер — это запасной путь, а не основной.** Сделать его единственным означает
потерять OpenGL-игры и положиться на поведение драйвера конкретного вендора.

### 2.5. Реальный формат CSV у PresentMon 2.5.1

Проверено на живом захвате. Колонки `FrameTime` **не существует** — frametime лежит в
`MsBetweenPresents` (индекс 10):

```
Application,ProcessID,SwapChainAddress,PresentRuntime,SyncInterval,PresentFlags,AllowsTearing,
PresentMode,TimeInMs,MsBetweenSimulationStart,MsBetweenPresents,MsBetweenDisplayChange,
MsInPresentAPI,MsRenderPresentLatency,MsUntilDisplayed,CPUStartTimeInMs,MsBetweenAppStart,
MsCPUBusy,MsCPUWait,MsGPULatency,MsGPUTime,MsGPUBusy,MsGPUWait,MsAnimationError,AnimationTime,
MsFlipDelay,MsAllInputToPhotonLatency,MsClickToPhotonLatency
```

Пример строки (обратите внимание на `NA` и на пробел внутри значения `PresentMode`):

```
Code.exe,18640,0x27A34FD9080,DXGI,0,0,0,Composed: Flip,199.8651,NA,119.21790000000000,
116.62900000000000,0.11920000000000,0.37630000000000,5.0455,80.7585,119.2258,119.1066,0.1192,
119.2792,0.2037,0.1955,0.0082,NA,80.7585,NA,NA,NA
```

Требования к парсеру:
- колонки искать **по именам заголовка**, никогда по позициям. Нормализация: нижний регистр,
  выбросить всё, кроме букв и цифр (`Process_ID` == `ProcessID`);
- алиасы frametime по приоритету: `msbetweenpresents` (2.5.1 и 1.x), `frametime` (часть сборок 2.x);
- `DisplayedTime` / `msbetweendisplaychange` — **это другая метрика** (время кадра на экране, у
  отброшенного кадра её нет). Использовать только по явному запросу, никогда как подстановку;
- `NA` — штатное значение, отбрасывать строку только если NA в колонке frametime;
- поддержать кавычки в ячейках (имя процесса может содержать запятую);
- кодировка: stdout и stderr идут в **UTF-16LE с BOM**; определять по BOM, снимать и UTF-8 BOM;
- схему фиксировать один раз из заголовка, дальше не перепроверять;
- заголовок **не считать** признаком успешного захвата (см. §2.7).

### 2.6. Поведение PresentMon 2.5.1 при ошибках

- Без элевации: выход с кодом **6**, в stderr `error: failed to start trace session: access denied.`
- Конфликт имени сессии: выход с кодом **1**,
  `warning: a trace session named "PresentMon" is already running and it will be stopped.`
- **Ловушка классификации:** при любом неэлевированном запуске печатается
  `warning: PresentMon requires elevated privilege in order to query processes that are
  short-running...` — включая запуски, которые дальше работают нормально. Разбирать **только**
  текст начиная с первой строки, начинающейся на `error`. Матчинг по всему stderr даёт ложный
  диагноз «нет прав» на рабочем захвате.

Проверенные флаги CLI (`--help` 2.5.1):
`--process_id <id>`, `--process_name <name>`, `--output_stdout`, `--no_console_stats`,
`--session_name <name>`, `--stop_existing_session`, `--terminate_existing_session`,
`--terminate_on_proc_exit`, `--timed <s>`, `--terminate_after_timed`, `--no_track_display`,
`--no_track_input`, `--no_track_gpu`, `--set_circular_buffer_size <n>`, `--v1_metrics`,
`--v2_metrics`, `--qpc_time_ms`, `--exclude_dropped`, `--etl_file <path>`.

`--v1_metrics` / `--v2_metrics` **не передавать**: они пинят набор метрик и ломают совместимость со
сборками, где их нет. Схема и так определяется по заголовку.

Целиться `--process_id`, а не `--process_name`: две копии одного exe иначе неразличимы.

### 2.7. Заголовок CSV — не измерение

Прежняя реализация выставляла статус AVAILABLE, как только читала заголовок. Заголовок приходит
сразу, кадры могут не прийти никогда. Состояние «измеряем» наступает только после первого
принятого кадра, а дальше держится watchdog'ом по таймеру, независимым от потока.

### 2.8. Блокирующее чтение потока нельзя ставить на путь управления

`read_line()` на stdout дочернего процесса неотменяем. Если читать его в той же задаче, которая
управляет сессией, молчащая игра блокирует смену цели и завершение приложения навсегда.
Чтение — на отдельном потоке; управляющая задача только супервизирует и завершает сессию, что и
разблокирует читателя.

### 2.9. GUID и keywords провайдеров

Снято с дампа реальной сессии PresentMon (`logman query "PresentMon" -ets`):

| Провайдер | GUID | Level | KeywordsAny |
|---|---|---|---|
| Microsoft-Windows-DXGI | `CA11C036-0102-4A2D-A6AD-F03CFED5D3C9` | 255 | `0x8000000000000002` |
| Microsoft-Windows-D3D9 | `783ACA0A-790E-4D7F-8451-AA850511C6B9` | 255 | `0x8000000000000002` |
| Microsoft-Windows-DxgKrnl | `802EC45A-1E99-4B83-9920-87C98277BA9D` | 4 | `0x8000841` (Base, Resource, LongHaul, Present) |
| Microsoft-Windows-Dwm-Core | `9E9BBA3C-2E38-40CB-99F4-9E8281425164` | 5 | `0x8000000000000081` |
| Microsoft-Windows-Kernel-Process | `22FB2CD6-0E7B-422B-A0C7-2FAD1FD0E716` | 4 | `0x8000000000000010` |
| Microsoft-Windows-Win32k | `8C416C79-D49B-4F01-A467-E56D3AA8234C` | 4 | `0x8400000440c01000` |

Для собственного ридера (§2.4) достаточно первых двух. Остальные — справочно: они показывают,
почему сессия PresentMon генерирует такой объём событий.

Для frametime **payload разбирать не обязательно**: `EVENT_RECORD.EventHeader` уже содержит
`ProcessId` и `TimeStamp`. Frametime = дельта между соседними `PresentStart` для нужного PID.
Адрес swapchain лежит в начале payload (указатель, 8 байт на x64) — нужен, только если разделять
несколько цепочек (§7.4).

### 2.10. Сенсоры железа

- **GPU-метрики через NVML.** `nvml.dll` поставляется с драйвером NVIDIA, отдельная установка не
  нужна, права администратора не нужны. Даёт всё, чего не хватало старому проекту: загрузка,
  температура, частоты ядра и памяти, VRAM used/total, питание, обороты вентилятора, а также
  потребление GPU **по процессу**. AMD — ADLX, Intel — IGCL.
- **LibreHardwareMonitor — не основной источник.** Это .NET-приложение, которое пользователь должен
  поставить и держать запущенным; читается через WMI `ROOT\LibreHardwareMonitor`. Годится как
  необязательное обогащение, не более.
- **Температура и питание CPU требуют драйвера режима ядра** (MSR/SMU). Поэтому свой драйвер везут
  и LHM, и HWiNFO, и Afterburner. Чисто user-mode приложение их надёжно получить не может.
  Решение принять явно (§5, D4).
- Загрузка CPU, частоты, RAM, процессы — обычный user-mode путь, crate `sysinfo`.

### 2.11. Собственный ETW-потребитель: проверено на работающем спайке

Установлено спайком `spikes/etw-frames` вместе с эталонным презентером `spikes/present-probe`.
Подробности и матрица — в `spikes/etw-frames/COVERAGE.md`.

- **`EVENT_TRACE_LOGFILEW` нельзя оставлять на стеке.** ETW сохраняет указатель на структуру,
  переданную в `OpenTraceW`, а не копирует её. Пока она была локальной переменной, callback'и
  не вызывались ни разу. Держать её живой всё время работы трейса.
- **Провайдеры включать до `OpenTraceW`.** При `EnableTraceEx2` после запуска `ProcessTrace`
  потребителю не доставалось ни одного события.
- Обе ошибки выглядят снаружи одинаково и обманчиво: `ProcessTrace` блокирует поток как
  положено и возвращает `ERROR_SUCCESS` при остановке сессии. Отличать «потребитель подключён,
  но событий нет» от «потребитель не подключён» нужно по отдельным счётчикам: события сессии
  (`ControlTrace(STOP)` заполняет `EventsLost`) против счётчиков самого потребителя.
- **Уборка сирот идёт по префиксу `MHMonitor-`, а не по собственному полному имени.** Сирота
  `MHMonitor-29244` от старого приложения обнулила захват, а уборка по узкому префиксу
  `MHMonitorSpike-` её не видела. Признак ровно такой, как в §2.1: постоянные потери, не
  зависящие ни от нагрузки, ни от настроек сессии.
- **`Present_Start` у DXGI — событие 42, `Present_Stop` — 43.** Подтверждено манифестом
  (`wevtutil gp Microsoft-Windows-DXGI /ge:true`: оба относятся к задаче 9, opcode 1 и 2) и
  совпадением их количеств в замере. У D3D9 это события **1 и 2** — проверено на GTA: San Andreas.
- **Payload разбирать ОБЯЗАТЕЛЬНО — §2.9 в этой части неверна.** За указателем на цепочку идут
  флаги (4 байта). `Rise of the Tomb Raider` вызывает `Present` с `DXGI_PRESENT_TEST` (0x1) ровно
  один раз на каждый настоящий кадр, и без фильтрации счёт удваивается: 595 FPS вместо ~300 по
  оверлею NVIDIA, с дельтами по 0.04 мс между «кадрами». PresentMon такие вызовы отбрасывает.
  Встреченные флаги: `0x1` — TEST, `0x200` — ALLOW_TEARING.
- **Бит `0x1` в событии DXGI не всегда означает `DXGI_PRESENT_TEST`.** Devil May Cry 4 SE —
  чистый D3D9 (в exe только `d3d9.dll`), но выводится через DXGI: провайдер D3D9 не дал ни одного
  события, а в событиях DXGI 42/43 бит `0x1` стоял на **всех** 1803 кадрах. Без фильтра они дают
  чистый ряд 179.9 FPS при 178 у PresentMon — это настоящие кадры, скорее всего с прокинутым
  `D3DPRESENT_DONOTWAIT`. Фильтр «бит `0x1` — тест» выбрасывал каждый кадр игры.
  - **Различать можно только по соседству на той же цепочке.** У Rise of the Tomb Raider каждый
    помеченный вызов идёт в паре с обычным через 0.04 мс (1 : 1) — это тесты. У DMC4 SE обычных
    вызовов нет вовсе — это кадры. Правило в коде: среди последних 32 вызовов цепочки обычных не
    меньше четверти от помеченных — помеченные тестовые; иначе — кадры. Первые 8 вызовов цепочки
    помеченные пропускаются без решения. **Это эвристика из двух измеренных случаев**, а не
    документированное поведение.
  - **Проверено вживую на обоих случаях.** DMC4 SE: 180.0 FPS собственным ETW при 178 у
    PresentMon. Rise of the Tomb Raider в одной сцене, прогоны подряд: 357.6 FPS собственным ETW
    против 350.0 у PresentMon; по счётчикам 6120 кадров и 6121 тестовый вызов, помеченных-кадров
    ноль — соотношение 1 : 1, как в P0.
  - **PresentMon этой неоднозначности не знает**: кадры он считает по событиям ядра (DxgKrnl), а
    не по событию рантайма. Ещё один довод за решение D1.
  - Первое объяснение было неверным и стоило лишней итерации: предположение «события идут от
    провайдера D3D9, где бит означает другое» проверил не спайком сразу, а исправлением кода.
    Уровень провайдера причиной тоже не был — у D3D9 `Present_Start` `level = 0`, как у DXGI.
- **Ошибка от тестовых Present выглядит правдоподобно** — просто «высокий FPS». Ловится только
  сверкой с внешним источником, поэтому сверка обязательна в приёмке каждого источника кадров.
- **Обратная ошибка выглядит как «источник не видит игру».** Отброшенные до единого кадры
  неотличимы от непришедших, если счётчики не выведены. Поэтому отчёт каждого источника несёт
  строку диагностики (сколько пришло, сколько отброшено и почему), и её показывают, пока кадров
  нет.
- **Покрытие, измеренное на NVIDIA в оконном/безрамочном режиме:** D3D9, D3D11, D3D12 и
  **Vulkan** видны; **OpenGL не виден** (Ion Fury, ноль событий за два прогона по 30 с при
  здоровой сессии). Эксклюзивный полноэкранный режим и другие вендоры не проверялись.
  Подробности и цифры — в `spikes/etw-frames/COVERAGE.md` §4.
- **На кадр может приходиться больше одной пары Start/Stop.** У одного из приложений
  одновременно шли DXGI 7/8 и DXGI 42/43/44 с одинаковой частотой. Фильтр строго по ID 42,
  иначе двойной счёт.
- **Уровень провайдера для Present не важен:** в манифесте у этих событий `level = 0`
  (LogAlways). 255 из §2.9 работает, 4 даёт то же самое с меньшим объёмом посторонних событий.
- **Размер и число буферов сессии ни на что не влияли** — проверены умолчания ETW, 8, 64 и
  128 КБ с разным числом буферов. Оставлять на усмотрение ETW.
- **Проверять себя нужно эталоном, а не глазами.** `present-probe` — настоящее D3D11-приложение,
  которое само считает свои `Present`. На 60 FPS спайк насчитал 60.0 FPS и 16.67 мс. Такой стенд
  не требует ни игр, ни сверки с чужим оверлеем и годится как регрессионный тест для P2.
- **`dwm.exe` презентит через DXGI постоянно и часто.** Выбор цели «по самому активному
  процессу» выберет его. Фильтр по PID обязателен.
- **`OpenTraceW` на несуществующей сессии возвращает успех.** Ошибка приходит только из
  `ProcessTrace`. Об успешном подключении потребителя судить можно лишь по статусу и моменту
  возврата `ProcessTrace`, а не по результату открытия.
- **Префиксы имени и уборки не совпадают — и это правильно.** Сессии спайка называются
  `MHMonitorSpike-<pid>` и **не** начинаются с `MHMonitor-`: дефис стоит в другом месте. Уборка
  идёт по `MHMonitor` без дефиса. Оба правила живут в одном модуле, `mh_core::session_name`, с
  тестами на их отношение — разъехавшись, они уже стоили вечера отладки.

### 2.12. Цепочка защиты от сирот: проверено убийством приложения

Сценарий §2.1 воспроизведён намеренно (фаза P2, программа `live_frames`): приложение с
работающим PresentMon снято через `taskkill /f`.

| Момент | PresentMon | Сессия `MHMonitor-<pid>` |
|---|---|---|
| до убийства | жив | работает |
| после убийства | **завершён** job object'ом | **осталась сиротой** |
| после следующего запуска | — | **остановлена** уборкой при старте |

Выводы, которые нельзя «упростить»:

- **Job object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` обязателен.** Без него PresentMon
  переживает приложение и продолжает держать сессию. Ядро закрывает задание при любой смерти
  процесса, в том числе когда `Drop` не выполняется.
- **Но сироту job object не предотвращает.** Он убивает PresentMon через `TerminateProcess`, и
  тот не успевает закрыть свою сессию (§2.2). Поэтому **уборка при старте обязательна**, а не
  «на всякий случай».
- **Обработчик консоли гасит сессию по имени прямо в себе.** При закрытии окна процесс
  завершается вскоре после возврата из обработчика, и до `Drop` дело не доходит.
- **После остановки PresentMon его сессию гасим мы**, по имени. Иначе каждая смена цели и каждый
  откат на запасной источник оставляли бы по сироте.

Слои, от внешнего к внутреннему: уборка при старте → обработчик консоли → job object → `Drop`.
Ни один из них не лишний: каждый закрывает случай, который остальные пропускают.

### 2.13. Живые игры через весь конвейер: что проверено и что это значит для UI

Фаза P2, программа `live_frames --source auto`, цель — окно в фокусе.

**PresentMon видит OpenGL, собственный ETW — нет.** Ion Fury: 178.9 FPS через PresentMon, ноль
событий через собственный потребитель (P0). Решение D1 подтверждено прямым сравнением. Кроме
того PresentMon дал кадры для D3D12 (Guardians of the Galaxy), Vulkan (Dota 2) и DMC4 SE; откат
не понадобился ни разу, гигиена чистая во всех прогонах. Таблица —
`spikes/etw-frames/COVERAGE.md`.

Наблюдения, которые нужно учесть в P4:

- **FPS по последнему кадру для показа непригоден.** У Dota 2 он скакал от 63 до 390 за
  секунду. Числом в HUD показывать FPS за короткое окно (порядка 0.5 с), а покадровые значения
  оставить графику.
- **1 % low за 30 с определяется единичными провалами.** У DMC4 одно подвисание уронило его со
  160 до 19, и потом значение полминуты медленно росло. Провалы часто приходятся на момент
  переключения в игру — стоит решить, отбрасывать ли первые секунды после смены цели.
- **Целью становится любое окно в фокусе, не только игра.** Первым кандидатом каждый раз был
  `powershell.exe`, и под него зря запускался PresentMon. В консольной программе это
  артефакт — окно консоли принадлежит родительскому процессу, — но браузер или редактор
  станут целью и в приложении. Так было и в Kotlin-версии; распознавание игр — отдельная задача.

### 2.14. Температура и мощность CPU через PawnIO (решение D4)

Проверено по первоисточникам в начале P3.

- **PawnIO** — подписанный драйвер ядра, который выполняет только подписанные модули на языке
  Pawn, а те отдают наружу узкие вызовы. Сырого доступа к железу из пользовательского режима нет —
  этим он и отличается от WinRing0, который Defender помечает как вредоносный. На PawnIO перешли
  LibreHardwareMonitor и Fan Control. Установщик — <https://pawnio.eu>.
- **Лицензии определяют способ связи.** Драйвер — GPL-2.0 с исключением для программ, которые
  общаются с ним **только через интерфейс IOCTL устройства**. Библиотека `PawnIOLib.dll` лежит в
  том же GPL-репозитории, поэтому с ней **не линкуемся**, а повторяем протокол сами через
  `DeviceIoControl`. Модули — LGPL-2.1; официальные подписанные сборки можно распространять с
  уведомлением.
- **Протокол.** Устройство `\Device\PawnIO`, тип устройства 41394, `METHOD_BUFFERED`.
  `IOCTL_PIO_LOAD_BINARY` (функция 0x821) загружает модуль в дескриптор;
  `IOCTL_PIO_EXECUTE_FN` (0x841) вызывает функцию модуля: на входе имя (32 байта, дополненные
  нулями) и массив `u64`, на выходе массив `u64`. Один дескриптор — один модуль.
- **AMD, семейства 17h–1Ah (Zen 1–5), модуль `AMDFamily17`.** `ioctl_read_msr` пропускает только
  белый список, в котором есть `MSR_PWR_UNIT` (0xC0010299) и `MSR_PKG_ENERGY_STAT` (0xC001029B) —
  мощность пакета считается по приросту счётчика энергии. `ioctl_read_smn` читает регистры SMN
  через пару «индекс/данные» PCI-устройства 0:0.0 и требует выравнивания смещения по 4 байтам.
- **Перед чтением SMN обязательно захватывать мьютекс `\BaseNamedObjects\Access_PCI`.** Пара
  регистров «индекс/данные» одна на всю систему; без мьютекса наше чтение перемешается с чтением
  HWiNFO или LibreHardwareMonitor, если они запущены.
- **Intel** — модуль `IntelMSR`. На этой машине (Ryzen 9 5900X) проверить его не на чем.
- **Отвергнутые варианты.** HWiNFO: разделяемая память в бесплатной версии отключается через
  12 часов. LibreHardwareMonitor: пользователь обязан держать чужое приложение запущенным, а сам
  LHM теперь всё равно требует PawnIO. Свой драйвер: EV-сертификат, подпись у Microsoft и
  ответственность за класс драйверов, которые попадают в блок-листы.
- **Проверено вживую** (`examples/live_hardware`, от администратора): Tctl 50–62 °C, мощность
  пакета 35–104 Вт; температура, мощность и все строки GPU совпали с оверлеем NVIDIA. Без прав —
  `ERROR_ACCESS_DENIED` при открытии устройства, секция CPU показывает «нужны права
  администратора».

### 2.15. Сенсоры железа: что выяснилось в P3

- **Первая загрузка CPU у `sysinfo` — всегда 0 %**: нужна пара замеров. Первое значение не
  показываем, секция в этот момент «без мнения», а не «сломана».
- **Частота CPU у `sysinfo` под Windows номинальная**: на 5900X всегда 3701 МГц, хотя с бустом
  реально ~4600 (сверено с оверлеем NVIDIA). Живая частота = `Processor Frequency` ×
  `% Processor Performance` / 100 из PDH, `\Processor Information(_Total)` — так считает
  диспетчер задач, прав не требует. Счётчики добавлять английскими именами
  (`PdhAddEnglishCounterW`) и читать с `PDH_FMT_NOCAP100`, иначе проценты обрезаются до 100 и буст
  пропадает. `sysinfo` остаётся запасным вариантом. Проверено вживую: 4485–4667 МГц в игре,
  совпадает с оверлеем NVIDIA.
- **VRAM по процессу через NVML под WDDM недоступна**: NVML всегда отвечает
  `NVML_VALUE_NOT_AVAILABLE`, памятью управляет ядро Windows. Нужна она — брать из счётчиков
  `GPU Process Memory` (PDH). В P3 не сделано.
- **«Не поддерживается» от NVML — не поломка.** Поле просто пустое, секция остаётся исправной.
  Частичной её делают только настоящие ошибки, сломанной — `GpuLost`.
- **Итог по железу — не худшее из секций**: машина без NVIDIA — нормальная машина. Всё исправно →
  `Available`, что-то читается → `Partial`, ничего → худшее.
- RTX 5070 Ti без прав администратора отдаёт всё, что показывает оверлей: загрузку, температуру,
  частоты ядра и памяти, VRAM, питание, обороты вентилятора.

### 2.16. Оверлей на egui: что выяснилось в P4

- **Прозрачность для мыши отдавать winit** (`ViewportCommand::MousePassthrough`). Он ставит
  `WS_EX_TRANSPARENT | WS_EX_LAYERED` и сам вызывает `SetLayeredWindowAttributes`; layered-окно
  без этого вызова не рисуется. Но при каждом переключении winit переписывает расширенный стиль
  целиком: `WS_EX_TOOLWINDOW` и `WS_EX_NOACTIVATE` пропадают, а `WS_EX_APPWINDOW` появляется и
  возвращает окно в Alt+Tab. Поэтому стиль переустанавливается раз в секунду вместе с topmost.
  Проверено на живом окне: без блокировки `0x8000198`, с блокировкой `0x80801B8`.
- **Пока окно скрыто, eframe не вызывает `ui`, только `logic`** — и только по
  `request_repaint`. Команды трея и хоткеев обрабатываются в `logic`, а их обработчики будят
  контекст; иначе скрытый оверлей нечем показать.
- **Позиция — в физических пикселях через Win32**, не через логические точки egui: при разном DPI
  мониторов точки пересчитывались бы по масштабу не того монитора. Сохранённая позиция
  проверяется `MonitorFromRect(MONITOR_DEFAULTTONULL)`; то же — раз в секунду на случай
  отключения монитора.
- **Сырой текст PresentMon в HUD не показывать, если причина сама — инструкция.** Без прав HUD
  писал «failed to start trace session: access denied»; теперь «нужны права администратора», а
  текст остаётся в `FpsState::detail`.
- **PresentMon запускать с `CREATE_NO_WINDOW`.** Из консольного примера он делил консоль с
  родителем, а у оконного приложения консоли нет — Windows открывала ему новое окно. Окно
  забирало фокус, трекер уводил цель на него, захват перезапускался по кругу; игра без фокуса
  проседала до 3–4 FPS, и это видел даже оверлей NVIDIA (DMC4 SE, от администратора).
- **PresentMon 2.5.1 теряет кадры в режиме `Composed: Copy with GPU GDI`.** DMC4 SE (DX10)
  в окне: игра и собственный ETW — 180 FPS, PresentMon — от 2 до 25 FPS с интервалами 3/91/17/87 мс
  (`target/pm-dmc4-windowed.csv`, 248 строк за 10 с), NVIDIA — 3–12. На полном экране без
  нашего окна — `Hardware Composed: Independent Flip`, 177 FPS (`pm-dmc4-fullscreen.csv`).
  Это не наша поломка и не нагрузка от опроса: `live_frames` без окна и без датчиков видел те же
  ~2 FPS. Прежний откат «нет кадров» тут не срабатывал: кадры идут, просто их мало.
  **Решено (пользователь):** откат по режиму вывода. Сеанс PresentMon помнит `PresentMode`
  последних 32 кадров; если после 8 кадров не меньше трёх четвертей из них — `Copy with GPU/CPU
  GDI`, сеанс завершается с `FpsReason::PresentModeUntracked`, и захват уходит на собственный ETW
  (липко, до смены цели). Режим, при котором это сработало, виден в подписи HUD.
- **Наше topmost-окно поверх полноэкранной игры переводит её в композицию.** Так пропадал счёт у
  NVIDIA, пока HUD был виден: игра уходила с Independent Flip, а заодно, вероятно, получала
  задержку композиции. Для пользовательского оверлея это неизбежно; учесть в §9 и в документации.
- **Откат по режиму — только для DXGI/D3D9.** Первая версия правила оставила Ion Fury (OpenGL,
  у PresentMon рантайм `Other`) совсем без FPS: в окне он тоже выводит через GDI-копию, откат
  уходил на собственный ETW, а тот OpenGL не видит. PresentMon такие кадры OpenGL считает (P2:
  178.9 FPS). Теперь кадр считается «потерянным», только если его рантайм — `DXGI` или `D3D9`.
- **`stop()` источников обязан быть идемпотентным.** Его зовут явно, а затем из `Drop`; второй
  вызов ждал уже забранное сообщение потока чтения и стоял полный таймаут — 2 с у PresentMon,
  5 с у собственного ETW (у него сообщение забирал ещё и `poll`). Отсюда долгий выход и медленная
  смена цели.
- **Трей и хоткеи — в своём потоке.** Меню трея (`TrackPopupMenu`) в потоке winit подвешивало
  цикл событий: HUD замирал (0 изменившихся пикселей за 8 с), «Настройки» и «Выход» лежали в
  очереди до первого движения мыши над оверлеем. Воспроизведено кликами по настоящему значку.
  Теперь поток `mh-tray` со своим циклом сообщений: настройки из трея открываются за 14 мс,
  выход — 73 мс. Будить надо именно корневое окно: `request_repaint_of(ViewportId::ROOT)`.
- **Масштаб HUD — до первого кадра.** `InnerSize` переводится в пиксели по масштабу на момент
  команды, а новый зум действует со следующего кадра; первый запрос уходил по 100 %, а кэш
  размера в точках не давал повторить. HUD был обрезан, пока не менялась его высота (5–10 с).
- **Молчащий запасной источник возвращает цель основному.** Ion Fury: PresentMon не дал кадров за
  5 с, собственный ETW OpenGL не видит — «липкий» откат оставлял игру без FPS навсегда. Если
  откат был из-за «нет кадров» и запасной тоже не увидел ни одного, захват возвращается на
  PresentMon и второй раз его не бросает: тот ждёт кадров сколько угодно.
- **OpenGL в окне — через событие ядра 184.** Ion Fury выводит через `Other · Composed: Copy with
  GPU GDI`: PresentMon видит 1–5 FPS, рантайм-провайдеры молчат. Пробник
  `examples/probe_dxgkrnl` нашёл у `Microsoft-Windows-DxgKrnl` события, идущие ровно на кадр
  (184, 166, 215 и др.); выбрано 184 (`Present`). Интервалы 184 совпали со счётчиком игры: 162 при
  лимите 165, 165–175 при ~180, 508–522 при ~520; интервалов короче 1 мс — ноль. Без фильтра поток
  DxgKrnl — 15–440 тыс. событий/с даже на уровне 4 и ключевом слове `0x1`; с фильтром
  `EVENT_FILTER_TYPE_EVENT_ID` (работает и для провайдера ядра) — ровно одно событие на кадр.
  Собственный ETW берёт кадры из 184, только пока рантайм цели молчит ≥ 1 с, — у DirectX-игр в
  окне ядро сообщает о тех же кадрах, и счёт удвоился бы. Откат по GDI-режиму теперь и для `Other`.
  **Проверено вживую:** `live_frames --source etw` на Ion Fury в окне — 152–154 FPS, ядро: 4329
  вызовов, 4181 кадр; оверлей показывает то же; DMC4 SE в окне — счёт не удвоился.
- **Ion Fury на полном экране закрывает HUD** (в безрамочном — нет). Вероятно, `Hardware: Legacy
  Flip` — вывод мимо композитора; проверить по строке «Вывод» в настройках.
- **Диагностика:** `FpsState::presentation` («Other · Hardware: Legacy Flip») видна в настройках,
  а `%LOCALAPPDATA%\MH Monitoring\MH-Monitoring.log` пишет шаги последнего запуска со временем.
  Окно настроек из работающего приложения открывается за 13–24 мс (без прав).
- **Порядок полей в payload `Present_Start` проверен: указатель, `Flags`, `SyncInterval`.**
  Повод: PresentMon пишет у DMC4 `PresentFlags = 0`, а собственный ETW видит у всех её вызовов
  бит 0x1. Проверка эталоном `present-probe` (`Present(sync, 0)`): при `--vsync 1` — 4176 кадров,
  помеченных 0; при `--vsync 0` — 142110 кадров, помеченных 0. Будь это `SyncInterval`, при
  `--vsync 1` помеченными оказались бы все. Значит, у DMC4 бит 0x1 в событии рантайма настоящий,
  а колонка `PresentFlags` PresentMon берёт значение не оттуда; эвристика §2.11 остаётся в силе.
- Попутно: при ~9000 FPS окно кольца упирается в ёмкость 16384 кадра меньше чем за 2 с — это
  штатно, статистика считается по последним 16384 кадрам.
- **График строится в движке**, в `Snapshot` уходит 240 столбцов, а не 16 тысяч кадров: в P6 это
  же пойдёт по IPC.
- **`%APPDATA%\MH Monitor\settings.json` занят Kotlin-версией.** Первый запуск Rust-оверлея
  перезаписал его, и старые настройки, кроме прозрачности, потеряны. Rust-версия пишет
  `settings-rs.json`; в P5/P7 путь не менять без явной миграции.
- **Переименование в MH Monitoring:** Rust-версия живёт в `%APPDATA%\MH Monitoring` и
  `%LOCALAPPDATA%\MH Monitoring`. При запуске UI `settings-rs.json` (и его карантин) переносится
  из `%APPDATA%\MH Monitor`, если в новой папке его ещё нет; `settings.json` Kotlin-версии
  остаётся на месте. `%LOCALAPPDATA%` не переносится: `bin` раскладывается заново, журналы —
  только последнего запуска.

## 3. Цели и не-цели

**Цели**
- Реальные показания: FPS, frametime, 1 %/0.1 % низкие, GPU, CPU, RAM.
- Накладные расходы, не влияющие на измеряемую игру.
- Честные состояния: если источника нет — сказать, какого и почему, а не показать прочерк.
- Один нативный исполняемый файл, установка без ручных действий пользователя.
- Работа поверх borderless-fullscreen.

**Не-цели**
- Никаких DLL-инъекций и хуков в игру (античит-риски, ложные срабатывания антивирусов).
  Всё измерение — только ETW и вендорские API.
- Не эксклюзивный fullscreen: туда user-mode overlay не попадает, это документируется, а не чинится.
- Не кроссплатформенность. ETW, WMI, layered-окна — Windows-only по природе.

```
│   │   ├── overlay.rs       # layered, click-through, topmost, DPI

│   │

│   │   ├── frames/
│   │   │   ├── presentmon.rs   # основной: дочерний процесс + CSV
│   │   │   └── etw_dxgi.rs     # запасной: свой потребитель
│   │   ├── gpu/
│   │   │   ├── nvml.rs
│   │   │   ├── adlx.rs
│   │   │   └── lhm_wmi.rs      # необязательное обогащение

│   │
│   ├── engine/          # владеет опросом, публикует Snapshot
│   ├── ipc/             # протокол служба ↔ UI (serde)
│   ├── service/         # windows-service, держит ETW
│   └── ui/              # egui/eframe, трей, окно настроек
└── assets/
    ├── fonts/           # Cuprum (перенести из старого проекта)
```

**Ключевое правило:** UI подписан только на `Snapshot` и не знает, откуда взялось число. Так же, как
в старом проекте — там это оправдало себя.

Предлагаемые крейты: `windows` (Win32/ETW), `nvml-wrapper`, `sysinfo`, `eframe`/`egui`, `serde` +
`serde_json`, `tracing` + `tracing-subscriber` + `tracing-appender`, `windows-service`,
`parking_lot`, `crossbeam-channel`. Версии не пинить в плане — брать актуальные на момент старта.

## 6. Фазы

Каждая фаза заканчивается рабочим состоянием. Порядок важен: сначала то, что определяет
жизнеспособность, потом то, что определяет удобство.

### P0 — спайк: собственный ETW-потребитель кадров

Отдельный бинарник, ничего общего с UI.

- `StartTraceW` c `EVENT_TRACE_REAL_TIME_MODE`, имя `MHMonitorSpike-<pid>`.
- `EnableTraceEx2` на DXGI и D3D9 (§2.9).
- `OpenTraceW` + `ProcessTrace` на отдельном потоке, callback `EventRecordCallback`.
- Фильтр по PID из `EventHeader`, frametime = дельта `TimeStamp` соседних `PresentStart`.
- `ControlTraceW(STOP)` на всех путях выхода, включая Ctrl+C и панику.

**Готово, когда:** получены реальные frametime для запущенной D3D12-игры, и **составлена матрица
покрытия** по API: D3D9 / D3D11 / D3D12 / Vulkan / OpenGL. Ожидание — Vulkan и OpenGL не видны
(§2.4); зафиксировать факт, а не предположение.

**Если спайк не даёт кадров** — сначала проверить сирот-сессии (§2.1), это самая вероятная причина.

### P1 — crate `core`: чистая логика, без Windows

Переносится по смыслу из старого проекта (§7). Никаких системных вызовов, 100 % юнит-тестами.

- `RingBuffer`: окно 30 с, ёмкость 16384, вытеснение и по времени, и по ёмкости, вытеснение
  срабатывает не только при записи (иначе при паузе старые кадры живут вечно).
- `statistics`: avg = N × 1000 / сумма frametime; 1 % low = 1000 / среднее самых медленных
  `ceil(N × 0.01)` кадров; 0.1 % аналогично. Минимумы выборки: 100 и 1000 кадров.
  Валидировать вход: отбрасывать `NaN`, `inf`, `<= 0`.
- `FpsState`: одна структура с `availability` + `reason` + `target` + `statistics` + `session_id` +
  `last_frame_at`. **Не разносить по отдельным каналам** — в старом проекте это давало
  несогласованные комбинации, и смена статуса без новых кадров не доходила до UI.
- `TargetProcess`: идентичность = PID **и** время старта. Windows переиспользует PID.
- `TargetTracker`: кандидат из foreground; смена цели только после debounce 750 мс; при уходе
  фокуса на shell/собственное окно цель удерживается; мёртвая цель сбрасывается немедленно,
  но накопленный debounce кандидата не обнуляется.
- `Aggregator`: слияние тиров по полям, TTL 4 с на монотонных часах.

**Готово, когда:** тесты покрывают границы 99/100/101 и 999/1000/1001 кадров, переиспользование
PID, Alt+Tab-удержание, истечение TTL. Ни одного `#[cfg(windows)]` в крейте.

### P2 — источники кадров

Трейт `FrameSource` с двумя реализациями и честным переключением.

`presentmon.rs`:
- вложенный exe, путь из ресурсов; явный пользовательский override поверх;
- команда: `--output_stdout --no_console_stats --terminate_on_proc_exit --session_name
  MHMonitor-<pid> --stop_existing_session --process_id <target>`;
- `--stop_existing_session` безопасен **только** потому, что имя наше (§2.1);
- чтение stdout на отдельном потоке (§2.8), stderr — отдельный поток с ограниченным хвостом;
- парсер по схеме заголовка (§2.5), счётчики `parsed` / `rejected` / `filtered`;
- классификация ошибок по тексту от первой строки `error` (§2.6);
- watchdog отсутствия кадров по таймеру: 5 с на старт, 2 с на разрыв уже идущего потока;
- гигиена сессий (§2.1) — подметание при старте, остановка на каждом пути выхода.

`etw_dxgi.rs`: продукт P0, доведённый до трейта.

Политика: PresentMon основной; при `UNSUPPORTED_CSV`, отсутствии кадров дольше N секунд или
невозможности запуска — переключение на собственный ETW с явным сообщением пользователю о том, что
источник сменился и Vulkan/OpenGL в этом режиме не покрываются.

**Готово, когда:** фейковый дочерний процесс покрывает молчащего ребёнка, только-stderr, access
denied, неподдерживаемую схему, 50 смен цели без утечки потоков и сессий; на живой игре получены
кадры от обоих источников.

### P3 — источники железа

**Сделано:** `hardware/{system,nvml,amd_sensor,sampler}.rs`, `SectionHealth` в core, пример
`live_hardware`. Не сделано: загрузка по ядрам (в `CpuStats` нет поля — добавить вместе с UI),
VRAM и загрузка по процессу цели (§2.15), Intel.

- `system.rs` через `sysinfo`: загрузка CPU (общая и по ядрам), частоты, RAM.
- `nvml.rs`: загрузка, температура, частоты, VRAM, питание, вентилятор; отдельно — VRAM и загрузка
  по процессу цели.
- Доступность **по секциям**, с кодом причины. Никаких прочерков без объяснения (§2.10).
- LHM через WMI — только если выбран вариант D4(а).
- Один GPU выбирается последовательно для всех полей; не смешивать поля разных адаптеров.

**Готово, когда:** на машине с NVIDIA заполнены все строки GPU, которые показывает вендорский
оверлей; при отсутствии NVML секция честно сообщает причину.

### P4 — overlay UI

**Сделано:** `core/graph.rs` (модель графика), крейт `engine` (потоки опроса, вложенный
PresentMon раскладывается в `%LOCALAPPDATA%\MH Monitoring\bin`), `platform/overlay.rs`, крейт `ui`
(бинарник `MH-Monitoring.exe`): HUD, трей, хоткеи Ctrl+Shift+F11/F10, перетаскивание, сохранение позиции.
Проверено без прав: вид, блокировка и скрытие хоткеями, стили окна. **Не проверено:** поверх
безрамочной игры, от администратора, при разном DPI и отключении монитора.

- egui/eframe, окно без рамки, прозрачное, always-on-top, раз в секунду заново забирает topmost
  (borderless-игра поднимается над topmost-окнами).
- Click-through через `WS_EX_TRANSPARENT` + `WS_EX_LAYERED` + `WS_EX_NOACTIVATE`.
- Перетаскивание, сохранение позиции, корректная работа при mixed DPI и отключении монитора.
- Трей: показать/скрыть, блокировка, настройки, выход.
- Глобальные хоткеи.
- **Читаемость:** прозрачность применять **только к фону**, текст оставлять полностью непрозрачным.
  В старом проекте alpha вешалась на весь контейнер, из-за чего текст блёк вместе с фоном.
- Шрифт Cuprum, ширина 272 dp, секции GPU / CPU / RAM / FPS — перенести как есть, это уже отлажено.

**График frametime** — переделать относительно старого:
- фиксированное временное окно (например 10 с), а не фиксированное число кадров: 180 сэмплов при
  240 FPS — это 0.75 с, при 60 FPS — 3 с, и график означает разное на разных играх;
- бакетирование по пикселям с сохранением пиков;
- база 0–20 мс, динамический потолок по устойчивой оценке (p95 × 1.25) с гистерезисом;
- одиночный выброс 500 мс не должен схлопывать нормальные 8–16 мс в ноль — ограничивать вершину
  с маркером;
- очистка при смене игры.

### P5 — настройки

**Сделано:** `ui/settings.rs` — схема v1 (оверлей, секции, строки, цель FPS, свой PresentMon,
хоткеи), миграция v0 → v1 (файл P4 без версии), починка значений после загрузки, карантин в
`settings-rs.corrupted.json`, атомарная запись, запись через секунду после последнего изменения.
`ui/settings_window.rs` — окно из трея (или `MH-Monitoring.exe --settings`): флажки и ползунки действуют
сразу, текстовые поля — черновик и «Применить»/Enter; свой PresentMon и хоткеи — после
перезапуска. Проверено вживую без прав: страницы, скрытие недоступных строк, запись и миграция
файла.

- **Окно настроек открывается рядом с HUD, а не под ним.** HUD висит поверх всех окон и закрывал
  меню разделов: клики уходили в HUD. Сторона выбирается по рабочей области монитора HUD.
- **Пока оверлей скрыт, окно настроек не рисуется** (eframe не вызывает `ui` скрытого корневого
  окна). Поэтому «Настройки» показывают оверлей, а скрытие оверлея закрывает настройки.
- **Масштаб HUD — зум всего контекста egui**, окно настроек масштабируется вместе с ним.

JSON, атомарная запись, дебаунс, карантин повреждённого файла, версионирование и миграция.
**Валидация после загрузки** — валидный JSON с отрицательной ёмкостью графика не должен ронять
приложение. Текстовые поля в UI — с моделью draft/apply, чтобы ввод символа не перезапускал захват.

### P6 — служба и неэлевированный UI

**Сделано:** крейт `ipc` (сообщения, упаковка «длина + JSON», версия протокола), `platform/pipe.rs`
(канал `\\.\pipe\MHMonitor`, SDDL: SYSTEM и админы — всё, интерактивные пользователи — чтение и
запись; удалённые клиенты отклоняются; `FILE_FLAG_FIRST_PIPE_INSTANCE` против захвата имени),
`platform/elevate.rs` (запуск себя через UAC), в `ui`: `server.rs`, `service.rs` (`--service`,
`--serve`, `--install-service`, `--uninstall-service`), `remote.rs`, `backend.rs`, раздел
«Служба» в настройках. Проверено без прав: UI ↔ `--serve`, падение и возврат сервера,
переход со своего движка на появившуюся службу.
**Проверено пользователем:** установка из настроек через UAC, игры с FPS и температурой CPU при UI
без прав администратора, повторный запуск UI с подключением к службе.

- **Цель выбирает UI.** Служба в сессии 0 не видит окна в фокусе пользователя; `TargetWatcher`
  живёт в UI и шлёт службе готовое `TargetResolution` при каждой перемене и раз в секунду.
  Нет клиентов — служба сбрасывает цель, PresentMon не работает впустую.
- **Служба запускает только вложенный PresentMon** из профиля SYSTEM (`systemprofile\AppData\Local`,
  обычному пользователю недоступен). Путь из настроек пользователя от SYSTEM не запускается —
  это было бы повышением прав.
- **Служба запускает тот exe, из которого её поставили.** Пока он лежит в `target\release`,
  любой пользователь может его подменить и получить SYSTEM. Для P7: ставить из Program Files.
- **Синхронный канал:** заблокированное чтение держит и запись, поэтому обе стороны читают только
  то, что показал `PeekNamedPipe`. `Drop` канала — только `CloseHandle`: `FlushFileBuffers`
  ждал бы зависшего клиента, `DisconnectNamedPipe` выбросил бы непрочитанное.
- **Без службы** UI работает как в P5, с движком в процессе, и раз в 3 с проверяет, не появилась ли
  служба.

- `windows-service`, служба владеет ETW-сессией и дочерним PresentMon.
- Протокол `ipc` через named pipe, serde; UI переживает перезапуск службы.
- UI запускается обычным пользователем, без UAC.
- Инсталлятор ставит службу; альтернатива — добавление в `Performance Log Users`.

### P7 — упаковка и приёмка

**Решено (пользователь):** один exe, который ставит себя сам; автозапуск — только флажком, по
умолчанию выключен.

**Сделано:** ресурсы exe (`crates/ui/build.rs`: иконка `assets/icon/MH-Monitoring.ico`, сведения о
версии из `Cargo.toml`, манифест `asInvoker` + PerMonitorV2), `ui/installer.rs` (`--install`,
`--uninstall`), `platform/{registry,shortcut,instance}.rs`, раздел «Установка» в настройках,
один оверлей на сеанс (`Local\MHMonitor-UI`), строка среды в журнале при старте.

- `--install` (UAC): снимает старую службу и закрывает оверлеи старой установки, копирует exe в
  `Program Files\MH Monitoring` через временное имя, ставит службу **на эту копию**, ярлыки в общем
  «Пуске» и на общем рабочем столе, запись в «Программы и компоненты»
  (`UninstallString` → `--uninstall`). Следы сборок до переименования (`Program Files\MH Monitor`,
  `mh-monitor.exe`, ярлык `MH Monitor.lnk`, автозапуск `MH Monitor`) убираются, включённый
  автозапуск переводится на новую копию.
- Скачанная копия после установки запускает установленную с `--after-install` и выходит;
  установленная ждёт мьютекс до 10 с.
- `--uninstall` сначала спрашивает «Да / Нет / Отмена»: удалять ли настройки и журналы. Без
  прав перезапускает себя через UAC с `--caller <pid>`: запущенный через UAC процесс удаляет
  установку и не трогает вызвавший процесс. Данные пользователя удаляет вызвавший процесс, у
  запущенного через UAC профиль может быть чужим. Папки удаляет скрытый PowerShell после выхода
  процессов, которые их держат (`Wait-Process`).
  Оверлей запускает `--uninstall` дочерним процессом без прав и читает код выхода:
  3 — отменено, 4 — данные удалены, тогда оверлей выходит и настройки не сохраняет.
- Первый запуск не установленной копии открывает настройки на «Установке». Отдельной кнопки
  «переустановить службу» нет: она поставила бы службу на скачанный файл.
- **Сборка:** `cargo build --release -p mh-ui` → `target\release\MH-Monitoring.exe` — это и есть
  дистрибутив.

- Один бинарник UI + служба, вложенные PresentMon (с NOTICE) и шрифты.
- Диагностика при старте в лог: версия сборки, среда, путь настроек, выбранные источники,
  путь и версия PresentMon, режим прав.
- Замер собственных накладных расходов: CPU, память, дескрипторы, потоки — в простое и в игре.
  Инструмент: `tools\measure-overhead.ps1 -Seconds 120 -Label "…"`. Скрипт берёт данные из WMI
  `Win32_PerfFormattedData_PerfProc_Process`, потому что пути `Get-Counter` на русской Windows
  локализованы. Прав не требует, отдельно показывает оверлей, службу и PresentMon.

  **Замер: простой** (2026-09-17, установленная копия со службой, рабочий стол, 24 логических
  ядра, 120 с). CPU — доля всей машины: 0,05 % — это примерно 1,2 % одного ядра.

  идёт собственным ETW в службе, а PresentMon не запущен (§2.16).

  Роста памяти и дескрипторов за время замеров не видно.

  **Ручной чек-лист §9, проверено пользователем 2026-09-17.** Работают: оконный и безрамочный
  режимы, перетаскивание, клики сквозь HUD, горячие клавиши, смена игры, закрытие игры, Vulkan,
  одновременная работа с оверлеем NVIDIA и Afterburner, несколько мониторов при 100/125/150 %.
  Найдено и исправлено (исправления проверены пользователем в тот же день):
  - **Эксклюзивный полноэкранный режим:** подсказки не было, кадр игры замирал, а при запуске сразу

    себя поверх всех окон, игра считала себя перекрытой и переставала рисовать. Теперь
    `overlay::exclusive_fullscreen_active` (`SHQueryUserNotificationState` =
    `QUNS_RUNNING_D3D_FULL_SCREEN`) раз в секунду проверяет режим. На это время оверлей
    прячется, не трогая настройку видимости, и не меняет порядок окон. Причина показывается в
    подсказке значка в трее, а после выхода из режима — 20 с в HUD. Проверено: и переход в
    режим во время игры, и запуск игры сразу в нём.
  - **Окно настроек закрывала безрамочная игра**, найти его можно было только через панель задач.
    Теперь окно настроек тоже поверх всех окон и при открытии получает фокус.

    кнопка «Запустить службу» (`--start-service` через UAC). Эта же команда включает
    перезапуск у старых установок.
  - **Alt+Tab в обычное приложение переводит цель** — см. наблюдение ниже.

  **Наблюдение:** переход из игры в обычное приложение (VS Code) дольше 0,75 с переводит цель на

  окне. Если это мешает, можно выбирать цель только среди окон, которые реально выводят кадры.
  Подсказка «OpenGL на весь экран может быть не виден» показывается при любом откате на
  собственный ETW, в том числе у D3D-игр. Она верна, но сбивает с толку. (Оба пункта закрыты в P8.)
- Ручной чек-лист (§9).

### P8 — после первого выпуска: AMD/Intel, выбор цели, лицензия

**Сделано:**

- **Видеокарты любого производителя — WDDM, а не ADLX/IGCL.** `platform/gpu.rs` читает ядро
  графики (`D3DKMTEnumAdapters2`, `D3DKMTQueryAdapterInfo`): имя, выделенную память, а через
  `KMTQAITYPE_ADAPTERPERFDATA` / `NODEPERFDATA` — температуру (десятые доли °C), обороты
  вентилятора, частоты памяти и ядра. Нули неоднозначны («вентилятор стоит» или «нет датчика»),
  поэтому поля включаются по `ADAPTERPERFDATA_CAPS` (`TemperatureMax`, `MaxFanRPM`). Загрузка и
  занятая память — PDH `GPU Engine(*)` и `GPU Adapter Memory(*)` (`CounterQuery::instances`),
  экземпляры помечены LUID адаптера (`luid_0x…_0x…`). Загрузка считается как в диспетчере задач:
  сумма по процессам для каждого движка, затем максимум по движкам (`hardware/gpu_counters.rs`).
  Мощности в ваттах этим путём нет: ядро даёт только долю от предела. `WddmGpuSensor` включается,
  когда NVML не поднялась; из нескольких карт берётся карта с наибольшей выделенной памятью.
  **Проверено** на RTX 5070 Ti (`examples/probe_gpu.rs`, NVML и WDDM рядом): температура, частоты
  ядра и памяти, вентилятор совпадают точно, VRAM — в пределах 20 МБ, загрузка — в пределах
  нескольких процентов (разные окна усреднения). На AMD и Intel не проверено: таких карт нет.
- **Температура и мощность Intel** — модуль PawnIO `IntelMSR` 0.2.11 из того же архива, что и
  `AMDFamily17` (хеш AMD-модуля в архиве совпал с проверенным). Формулы `coretemp`/`rapl`:
  TjMax из `IA32_TEMPERATURE_TARGET[23:16]` (0 → 100 °C), температура пакета =
  TjMax − `IA32_PACKAGE_THERM_STATUS[22:16]`; без датчика пакета (CPUID.06H:EAX[6]) —
  `IA32_THERM_STATUS` с битом действительности 31. Мощность — `PKG_ENERGY_STATUS` тем же
  `EnergyMeter`, что у AMD. Процессор без цифрового датчика (CPUID.06H:EAX[0]) — «не
  поддерживается». **Проверено только тестами расшифровки:** на машине разработчика AMD.
  `AmdSensorError` стал общим `CpuSensorError`.
- **Правило 2а выбора цели** (`core/target.rs`, `SwitchGuard`): цель, у которой идут кадры,
  отдаётся только кандидату, который сам рисует. «Рисует» — загрузка 3D-движков процессом не
  ниже 10 % (`engine/watcher.rs`, PDH `GPU Engine`, снимается только когда вопрос решает дело).
  Порог выбран замером: Chrome в работе давал 5,5 %, VS Code — 0,2 %. Кандидат, которого правило
  не пропустило, остаётся кандидатом и сменит цель сразу, как начнёт рисовать. Без кадров у цели
  и без цели правило не действует.
- **Подпись об откате на собственный ETW:** пока кадры идут, предупреждение про OpenGL не
  показывается; при выводе через GDI — короткая строка «кадры считает собственный ETW (вывод
  через GDI)».
- **Лицензия MIT** (`LICENSE`, `license.workspace` во всех крейтах); сторонние компоненты — со
  своими лицензиями (PresentMon — MIT, модули PawnIO — LGPL-2.1+, Cuprum — OFL 1.1).
- Скриншот HUD для README снимается поверх чёрной подложки: за полупрозрачным фоном HUD иначе
  видно содержимое экрана.

### P9 — первый запуск, полноэкранный режим, цепочка поставок

**Повод.** Пользователи не читали README, не ставили службу, и FPS не появлялся: первый запуск
открывал настройки на «Установке», их просто закрывали. Второй повод — атака на `arrayref`
(2026-08-20): после взлома учётной записи автора на crates.io вышли версии с зависимостью от
вредоносного `proc-macro1`, чей `build.rs` скачивал вредоносную программу. В `Cargo.lock` и в
кэше cargo этих крейтов нет (проверено 2026-09-17). Но служба выполняет код зависимостей от
SYSTEM, и такая атака дала бы права системы.

**Решено (пользователь):**
- служба остаётся основным путём, но выбор нельзя пропустить: окно первого запуска;
- в эксклюзивном полноэкранном режиме два поведения на выбор: скрывать HUD или переносить его
  на другой монитор; выбор делается и до установки;
- CI с `--locked` и `cargo deny`, служба — отдельный бинарник.

**Сделано:**
- **Окно первого запуска** (`ui/setup_window.rs`). Показывается, если `setup_done` не стоит,
  копия не установленная, процесс без прав и служба не отвечает. Варианты:
  - «Установить» — `--install` через UAC; окно закрывается, когда установка удалась;
  - «Только сейчас — от администратора» — `elevate::launch_elevated(exe, "--relaunched")`, эта
    копия выходит, новая ждёт мьютекс, как после установки. `setup_done` не ставится: без прав
    окно спросит снова;
  - «Продолжить без FPS».

  Флажок автозапуска применяется при любом выборе. Схема настроек v2: файл v1 получает
  `setup_done = true`, у тех, кто программой уже пользовался, окно не появляется. Настройки
  открываются на «Установке» только если установлена другая версия, чем запущена.
- **Остановленная служба запускается сама.** Через 5 с после старта, если программа установлена,
  снимки свои и служба в состоянии `Stopped` (не `StartPending`: при входе в систему служба ещё
  поднимается), оверлей один раз просит `--start-service` через UAC.
- **Эксклюзивный полноэкранный режим:** `overlay.fullscreen` = `hide` | `other_monitor`,
  незнакомое значение даёт умолчание, а не карантин файла. `other_monitor`: монитор игры —
  `MonitorFromWindow(GetForegroundWindow())`, цель — рабочая область монитора без пересечения с
  ним, основной предпочтительнее (`overlay::other_work_area`, тесты на раскладках). HUD встаёт в
  угол с отступом 20 px, порядок окон не трогается (`bring_to_top` не зовётся), позиция в
  настройки не пишется. После выхода из режима HUD возвращается на прежнее место. Монитор один,
  HUD скрыт или место не найдено — прячется, как раньше.
- **Внедрение в процесс игры не делается.** Это противоречит принципу проекта (§1: без DLL и
  хуков) и бьёт по античитам.
- **Служба — отдельный `MH-Monitoring-Service.exe`** (крейт `mh-service`: `server.rs` и
  диспетчер SCM). Её дерево — 61 крейт против 174 у оверлея: eframe, winit, tray-icon,
  global-hotkey в процесс SYSTEM не попадают. Это важно и потому, что код инициализации из
  секций `.CRT$XCU` выполняется при загрузке образа, даже если режим до него не доходит.
  Журнал переехал в `mh-platform::diag`, `SERVICE_NAME` и `SERVICE_EXE_NAME` — в `mh-ipc`.
  - Дистрибутив по-прежнему один файл: `ui/build.rs` встраивает службу
    (`MH_SERVICE_EXE` или `target\<профиль>\MH-Monitoring-Service.exe`) в `OUT_DIR/service.bin`.
    Если файла нет, встраивается пустой файл и выдаётся предупреждение сборки.
  - Установщик берёт службу из файла рядом с запущенным exe, иначе из встроенной копии, и
    кладёт её в Program Files через временное имя. Служба ставится на неё.
  - `MH-Monitoring.exe --service` теперь отказывает: регистрация из версий до 0.2.0 иначе
    запустила бы оверлей от SYSTEM в сеансе 0. Настройки в этом случае предупреждают, что служба
    стоит не на установленной копии; «Обновить установленную» перерегистрирует её.
  - Версия 0.2.0: у установленной 0.1.0 другая раскладка, и запущенная новая копия предлагает
    обновление.
- **Цепочка поставок:** `deny.toml` — только цель `x86_64-pc-windows-msvc`, RustSec, отозванные
  версии запрещены, источники только crates.io, список лицензий по факту дерева. Крейты помечены
  `publish = false`, иначе `cargo deny` считает пути без версий «звёздочками».
  `tools\build-release.ps1`: служба, затем оверлей с `MH_SERVICE_EXE`, оба `--locked`; проверка,
  что служба встроена; `target\dist` с `SHA256SUMS.txt`. Встраивание проверено сравнением
  байтов. `.github/workflows/ci.yml`: fmt, clippy `-D warnings`, тесты, `cargo check` под
  Linux, `cargo deny --locked check` (и по расписанию раз в неделю), релизная сборка как
  артефакт. Действия закреплены по SHA, `permissions: contents: read`, `persist-credentials:
  false`.
- **Автозапуск с наивысшими правами через Планировщик не сделан.** Задача с `HighestAvailable`
  запускает файл без UAC. Если файл лежит там, куда пишет пользователь, это обход UAC для
  любого процесса этого пользователя. Для копии в Program Files задача не нужна: там есть
  служба.

**Не проверено вживую** (нужен UAC и второй монитор с игрой в эксклюзивном режиме): установка
из окна первого запуска, «Только сейчас», автозапуск остановленной службы, обновление с 0.1.0,
перенос HUD на другой монитор. Проверено: сборка, тесты, clippy, `cargo deny`, релизный
скрипт, запуск нового оверлея с чистыми настройками при работающей службе 0.1.0 (подключился,
окно первого запуска не показано, как и задумано).

### P10 — старые игры: запуск в окне и окно без рамки

**Повод.** Warcraft III 1.26 (Direct3D 8) работает только в настоящем эксклюзивном
полноэкранном режиме, поверх которого окна не видны; безрамочного режима в меню нет. Но у игры
есть параметр `-window`.

**Решено (пользователь):** программа сама запускает игру с параметрами и делает её окно
безрамочным на весь монитор. Своё внедрение в игры (перехват Present) и вывод через RTSS не
делаются.

**Сделано:**
- Профили игр в настройках (`games`: имя, путь, параметры, `borderless`, `window_exe`). Имена
  уникальны без учёта регистра и годятся для имени файла: из них делается ярлык. Профиль без
  пути отбрасывается. Пресет Warcraft III: `Frozen Throne.exe` / `Warcraft III.exe` →
  `-window`, окно `war3.exe` (загрузчик передаёт параметры и выходит); `war3.exe` →
  `-window`.
- Раздел «Игры»: добавление через системный диалог (`platform::dialog`, `IFileOpenDialog` в
  своём потоке, владелец — скрытое topmost-окно того же потока, иначе диалог открывался бы под
  окном настроек) или путём; параметры правятся на месте; «Запустить», «Ярлык на рабочем
  столе», «Удалить».
- `--launch "<имя>"` (`ui/games.rs`): запускает игру из профиля (рабочая папка — папка игры),
  ошибку показывает окном; дальше обычный оверлей, который при уже работающем выходит.
  Ярлык — на рабочем столе пользователя (`SHGetKnownFolderPath`), цель — установленная копия,
  если она есть, значок — из файла игры (`shortcut::create_with`).
- `BorderlessWatcher` раз в секунду (в уборке оверлея) смотрит окно на переднем плане. Если его
  процесс — файл окна профиля **в папке игры** (иначе задело бы редактор карт или одноимённый
  файл другой игры), `game_window::make_borderless` снимает `WS_CAPTION | WS_THICKFRAME |
  WS_SYSMENU | WS_MIN/MAXIMIZEBOX` и рамочные расширенные стили и ставит окно на весь его
  монитор (`SWP_FRAMECHANGED`). Невидимые, дочерние окна, диалоги (`#32770`) и окна меньше
  320×200 не трогаются. Повтор для того же окна — не чаще раза в 5 с: игра может возвращать
  рамку сама. `ERROR_ACCESS_DENIED` (игра от администратора, UIPI) — строка в HUD.
- **Проверено вживую:** тестовое окно WinForms 800×600, запущенное через `--launch` из
  профиля, через 1,3 с стало 2560×1440 на своём мониторе, в журнале — «окно без рамки на весь
  монитор». На Warcraft III не проверено: игры на машине разработчика нет. Диалог выбора файла
  вручную не проверен.

## 8. Тестирование

- **Юнит-тесты** — весь `core`, парсер CSV, гигиена имён сессий. Запускаются где угодно, без

  ```powershell
  rustup target add x86_64-unknown-linux-gnu
  cargo check -p mh-core -p mh-sources --target x86_64-unknown-linux-gnu
  ```

- **Windows-интеграционные** — отдельный набор, помеченный `#[ignore]`, требует прав. Реальный
  запуск PresentMon, реальная ETW-сессия, NVML.

## 9. Ручной чек-лист приёмки

| Сценарий | Критерий |
|---|---|
| Оконный режим | Overlay виден, значения обновляются |
| Borderless fullscreen | Overlay поверх, игра держит фокус |
| Эксклюзивный fullscreen | Ограничение объяснено в UI, не «молча не работает» |
| Drag / click-through / хоткеи | Работают из игры, конфликт хоткея диагностируется |
| Выход через трей | Ни одного `PresentMon.exe`, ни одной сессии `MHMonitor-*` |
| Принудительное убийство приложения | Сирота подметается при следующем старте |
| Смена игры | История очищается, новая сессия, старые цифры не «живут» |
| Alt+Tab | Цель удерживается, захват не перезапускается |
| Игра закрыта | Честный статус, а не замерзшие последние значения |
| Vulkan-игра | На PresentMon работает; при откате на свой ETW — явное сообщение |
| Параллельный монитор | Чужая ETW-сессия не останавливается |
| Мультимонитор, 100/125/150 % DPI | Позиция восстанавливается, ширина не скачет |
| Чистая система без драйверов | Понятные причины, а не прочерки |

---

## 10. Риски

| Риск | Смягчение |
|---|---|
| Свой ETW-ридер не покроет часть игр | PresentMon остаётся основным; покрытие меряется в P0 |
| CPU temp/power недостижимы без драйвера | Решение D4 принять до вёрстки HUD |
| Служба усложняет отладку и установку | Протокол `ipc` определить рано, разделение — отдельной фазой |
| Сирота ETW снова сломает захват | Требования §2.1 закрыты тестами, не только кодом |
| egui окажется тесен для HUD | UI отделён от `engine`; замена не трогает телеметрию |
| Соблазн «упростить» гигиену сессий | Комментарии с причиной рядом с кодом, тест на каждое требование |

---

## 11. Первый шаг

Начинать с **P0**. Он отвечает на единственный вопрос, который определяет жизнеспособность
собственного источника кадров, и делается за вечер. Всё остальное — известная инженерия.

Перед запуском любого замера проверять `logman query -ets` на сирот `MHMonitor-*` и `PresentMon`.
Половина «необъяснимых» нулей объясняется именно ими.
